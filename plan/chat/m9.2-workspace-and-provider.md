## Scope

Everything needed to connect to OpenRouter, pick a model, send a message and stream an answer — **with no grounding, no context, no citations, no history**. Those are M9.3.

The exit state is deliberately an ungrounded chatbot, which is exactly what the plan says not to ship. It therefore sits behind a build flag that stays off in production until M9.3 exits. Do not skip §7 of this document.

## Do not do these

- **Do not extract a shared `SideWorkspace` component.** `SearchDrawer`'s focus trap carries a special case for its nested mobile filter sheet (`SearchDrawer.tsx:72`) that only it needs. Copy the drawer mechanics into `ChatDrawer`. Extraction happens in M9.5, once two real consumers show what is genuinely common. M7.5 accessibility is explicitly at risk here.
- **Do not add `"chat"` to `PaneSourceType`** in `state/store.ts:5`. Reader panes stay dedicated to canonical content and notes.
- **Do not add a provider SDK.** OpenRouter needs only a small standards-based client, and an SDK would add weight without removing the need to handle SSE and OpenRouter metadata. Raw `fetch` + a hand-written SSE parser.
- **Do not build OAuth.** Deferred to M9.6 (`../interactive_chat_plan.md` §5.5).
- **Do not persist the API key anywhere but `sessionStorage`.**

| id | baseUrl | modelsPath | modelsNeedAuth | validatePath | extraHeaders | cspOrigin |
|---|---|---|---|---|---|---|

### 1a. `validatePath` is separate from `modelsPath` — and this is not a nicety

The original parent plan proposed validating a key through the models endpoint. **For OpenRouter that cannot work**: `GET /api/v1/models` requires no authentication and returns HTTP 200 with the full catalogue no matter what the `Authorization` header contains — the same property that makes the pre-connect picker possible (`m9.0-findings.md` §1, §11). Validating through it accepts any string, including an empty one, and the user discovers their key is wrong when their first question dies mid-stream. `../interactive_chat_plan.md` §6 is now corrected to require `/api/v1/key`.

Use `GET https://openrouter.ai/api/v1/key` with `Authorization: Bearer <key>`. It is documented for exactly this. Two fields from its response feed UI the plan already wants:

- `limit_remaining` → available key metadata, from a real source rather than an estimate. **Not consumed in M9.2**: `../interactive_chat_plan.md` §7.2 specifies no credit display, and the 2026-07-30 decision is not to add one — recorded here only so a future proposal knows the field exists.
- `is_free_tier` → which OpenRouter rate limit applies (50/day vs 1,000/day, §4 of the findings), so the rate-limit error can name the actual number.

**CORS check completed 2026-07-29:** an `OPTIONS` preflight from `https://bible.trendafilovi.net` returned 204, and an actual GET with a deliberately invalid bearer token returned a browser-readable 401. Both carried `access-control-allow-origin: *`. No real key was used for this check.

`modelsNeedAuth: false` must never be read as "validation is free".

### 1b. `satisfiesNoTraining` — what the licence gate consults

M9.1 ships `ai_context_policy = allowed_no_training` for works whose licence permits AI use only under no-training and no-retention terms. With OpenRouter, **two independent conditions** must hold:

1. `privacyRouting` is on, so every request sends `zdr: true` + `data_collection: "deny"`. OpenRouter fails closed when no eligible endpoint exists, and documents that the same filters apply to upstream BYOK endpoints.
2. The user confirms for this tab session that OpenRouter's **own** Input/Output Logging and OpenRouter Use of Inputs/Outputs settings are disabled for their account/workspace. OpenRouter says these opt-ins are off by default, but the API does not expose their state and per-request ZDR cannot turn them off.

```ts
export function satisfiesNoTraining(settings: ChatSettings): boolean {
  return settings.privacyRouting && settings.openRouterLoggingDisabledConfirmed;
}
```

The confirmation defaults false, is stored in `sessionStorage` only, and is cleared on Disconnect. If either condition is false, `allowed_no_training` sources appear disabled with an actionable reason. This is an eligibility gate, not a warning.

It is still an attestation, not technical proof of account state. A work whose licence requires the app to verify that logging is off cannot use this path and must be `prohibited`; do not weaken that licence into an unchecked UI promise.

OpenRouter also documents anonymous categorization of a small prompt sample using a ZDR model even when logging/use opt-ins are off. This is not training or prompt retention, but it is processing that the privacy notice and any negotiated content permission must cover.

Direct providers are deliberately absent — **do not re-add one without a separate terms and architecture review**:

- **`api.openai.com`** — its completions response omits `Access-Control-Allow-Origin` even though the preflight passes. A curl test will tell you it works; a browser will not. OpenAI models are reachable through OpenRouter.
- **`api.anthropic.com`** — technically reachable (M9.0 §1a), but a direct adapter needs an Anthropic API key, and a Claude Pro subscription is not one: consumer plans and API access are separate billing pools. OpenRouter carries 26 Claude models at the same published rates, including `anthropic/claude-haiku-4.5` at $1/$5 per million. See the parent plan §5.4a.
- **`generativelanguage.googleapis.com`** — technically reachable, but accepting a user's Google AI Studio key leaves that direct Google use under Google's terms. OpenRouter cannot turn such a key into a different entitlement. Gemini-branded models may still be selected from OpenRouter's catalogue, but the app never receives a Google key.

The app also does not create or manage provider BYOK credentials inside OpenRouter. A user may have configured them independently in their workspace; OpenRouter prioritizes matching BYOK endpoints and reports `usage.is_byok`. The app displays that metadata when returned, while the user remains responsible for the upstream terms. OpenRouter documents that BYOK does **not** bypass `zdr` or `data_collection` filtering.

Model-picker fields from the OpenRouter catalogue: `id`, `name`, `context_length`, `pricing.prompt`, `pricing.completion`, and `"tools" in supported_parameters`.

A unit test asserts every `cspOrigin` in the registry appears in the deployed CSP string. That test is what stops a provider being added without its origin.

## 3. SSE parser — `apps/web/src/chat/sse.ts`

The single most bug-prone piece. Write it standalone and test it hard before wiring it up.

```ts
export async function* parseSse(
  body: ReadableStream<Uint8Array>,
  signal: AbortSignal,
): AsyncGenerator<SseEvent>;
```

Must handle:

- Events split across chunk boundaries **mid-line and mid-UTF-8-sequence** (use a single `TextDecoder` with `{ stream: true }`; do not decode per chunk).
- `data:` lines with and without a leading space.
- Comment lines starting with `:` (keep-alive) — ignored.
- Multi-line `data:` accumulation within one event.
- `data: [DONE]` terminator.
- Malformed JSON in one event → skip that event, keep the stream alive; do not abort the answer over one bad frame.
- `signal.abort()` → cancel the reader, resolve cleanly, no unhandled rejection. **Verified working** on OpenRouter in M9.0.
- A stream that ends without `[DONE]` → treated as truncated, not as success.
- **Discard `delta.reasoning` and `delta.reasoning_details`** (§4b). Real streams carry them; the plan forbids storing chain-of-thought.

Tests feed a mock `ReadableStream` with deliberately hostile chunking: one byte at a time, a chunk boundary inside a multi-byte Cyrillic character, an event split across three chunks.

### 4a. OpenRouter usage metadata

Without an explicit opt-in, the streamed response carries no usage and the cost display has nothing to read. Every shipped request sends:

```json
{ "usage": { "include": true } }
```

`usage: {include: true}` is an OpenRouter extension, not standard OpenAI. Use `total_tokens` for any cost display, not `prompt + completion`, and carry `is_byok` into the visible run metadata when returned.

### 4b. Reasoning suppression is mandatory, not an optimisation

M9.0 found that `openrouter/free` with `max_tokens: 160` streamed 160 chunks and produced **an empty answer**: the whole budget went to hidden reasoning (`reasoning_tokens: 188`, `finish_reason: "length"`, `content: ""`). Shipped without suppression, a user's first question can stream for fourteen seconds and show nothing.

| Provider | What to send | Notes |
|---|---|---|
| OpenRouter, reasoning not marked mandatory | `reasoning: { enabled: false }` | Verified on `openrouter/free`: `reasoning_tokens: 0`, `finish_reason: "stop"`, full content |
| OpenRouter | ~~`reasoning: { exclude: true }`~~ | **Does not work.** Only hides the output; the budget is still consumed and content still comes back empty |
| OpenRouter model with `reasoning.mandatory: true` | no disable flag | Raise the answer budget and retain the typed `emptyAnswer` path |

**This is why `suppressReasoning` takes a capability argument.** Reasoning suppression is a property of the *model*, and an unconditional flag would be rejected by mandatory-reasoning models:

```ts
export interface ModelReasoningCaps {
  mandatory: boolean;             // OpenRouter: "do not send effort:'none' — the model rejects it"
  supportedEfforts?: string[];
  supportsMaxTokens?: boolean;
}
```

- **OpenRouter** exposes this per model on `GET /api/v1/models` under a `reasoning` object (`mandatory`, `supported_efforts`, `default_effort`, `default_enabled`, `supports_max_tokens`). Read it in `listModels()` and carry it on `ChatModel`.
- **`caps === null` means unknown.** Dynamic routers — `openrouter/free` included — omit the `reasoning` field. For OpenRouter, send `reasoning: {enabled: false}` when caps are absent because that exact router was measured and otherwise commonly returns an empty answer. If OpenRouter rejects suppression for the selected route, surface a typed model-capability error; do not silently retry a potentially billable request without suppression.

**When metadata says suppression is unavailable, the fallback is budget**, not hope: raise `max_tokens` far enough above the expected answer that hidden reasoning cannot consume all of it, and keep the `emptyAnswer` error for when it still does.

The SSE parser must also **discard** `delta.reasoning` and `delta.reasoning_details` — confirmed present in real streams. The plan forbids storing chain-of-thought (§12), so drop them explicitly rather than relying on them being ignored.

Treat `finish_reason: "length"` with empty content as its own typed error (`emptyAnswer`), not a blank message. With mandatory-reasoning models it is a *likely* path, not an edge case, so its message must suggest raising the answer cap or changing model.

### 4c. Resulting request body

```jsonc
{
  "model": "...",
  "messages": [...],
  "stream": true,
  "max_tokens": 1500,
  "usage": { "include": true },
  // via providerConfig.suppressReasoning()
  "reasoning": { "enabled": false },
  // only when providerConfig.supportsPrivacyRouting && privacyRouting
  "provider": { "zdr": true, "data_collection": "deny" }
}
```

Retry policy: at most two retries, exponential backoff, honour `Retry-After`. **Never** retry 401, 402, 403, or a user abort.

## 5. Errors — `apps/web/src/chat/errors.ts`

```ts
export type ChatErrorKind =
  | "auth"            // 401/403 -> "check your key"
  | "credit"          // 402     -> "add credit at <provider>"
  | "rateLimit"       // 429     -> retryAfter seconds
  | "modelUnavailable"
  | "privacyConstraint"  // 404: no endpoint satisfies zdr/data_collection — COMMON, see below
  | "emptyAnswer"        // finish_reason "length" with no content (reasoning ate the budget)
  | "network"
  | "malformedStream"
  | "aborted";

export class ChatError extends Error {
  readonly kind: ChatErrorKind;
  readonly retryAfterSeconds?: number;
  // Never carries a provider response body, prompt, key, or source text.
}
```

Map HTTP status → kind in one place. Each kind gets an i18n key and a concrete next action.

`privacyConstraint` is not theoretical — M9.0 measured that **most individually named free OpenRouter models return HTTP 404** under `zdr + data_collection: deny` (`"No endpoints found matching your data policy"`), while `openrouter/free` succeeds because the router filters to compliant endpoints. Any user who picks a named free model from the catalogue will hit this. The message must name the cause and offer the two real options: switch model, or relax the privacy setting with a clear warning.

- API key input: `type="password"`, `autoComplete="off"`, never pre-filled with the stored value — show a "Connected" state instead of echoing it back.

- Connect → `validateKey()` → store on success; show a typed error on failure. A bad key must fail here, not mid-answer.

- Model picker: `listModels()` with a text filter (OpenRouter lists hundreds). Show id, context length and price. For OpenRouter this loads before connecting (`modelsNeedAuth: false`) so a first-time user can browse.

The picker opens with no selection and the Assistant cannot send until the user chooses. `openrouter/free` passes ZDR + `data_collection: deny` but produced unusable Bulgarian in two of four samples, one of them a content-safety classifier that replied `"User"` — a default that returns gibberish half the time reads as a broken app, not as free-model variance. Do not preselect anything, and do not present free models as the recommended path. Revisit only against [`m9.0b-2-bulgarian-quality.md`](m9.0b-2-bulgarian-quality.md), which runs after M9.3.
- Privacy routing toggle, shown only when `supportsPrivacyRouting`. Default on.
- **OpenRouter logging confirmation** — a checkbox, default off and session-scoped: *"I confirm Input/Output Logging and OpenRouter Use of Inputs/Outputs are disabled for this OpenRouter account/workspace."* Explain that this is relied on only for sources marked `allowed_no_training`; while it is off, those sources are excluded.
- OpenRouter privacy note from [`m9.0-findings.md`](m9.0-findings.md) §10c. Distinguish upstream routing controls from OpenRouter's own optional account logging.
- Disclose OpenRouter's anonymous ZDR categorization separately; do not describe ZDR as meaning that no system processes the prompt.
- Terms/eligibility notice at Connect: the user must use their own OpenRouter account, be at least 13 (and have parent/guardian permission when under 18), follow OpenRouter and applicable Model Terms, and have the rights needed for their question and any selected notes. Link OpenRouter's current Terms and its Model Terms section; require an explicit session acknowledgement before Connect.
- The model picker links the selected model's OpenRouter detail page and repeats that upstream Model Terms may apply. OpenRouter's public model catalogue does not expose a machine-readable terms field, so the app must not claim it has verified model-specific eligibility for the user.
- OpenRouter's current Terms may require buying credits (minimum purchase currently $5). Do not market `:free` as guaranteed zero-cost onboarding.
- Upstream-key boundary: the app never asks for Google, Anthropic, OpenAI, or other provider credentials and does not configure OpenRouter BYOK. If OpenRouter reports `is_byok`, show that status on the answer.
