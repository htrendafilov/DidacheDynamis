# M9.1 — Content licence metadata (`ai_context_policy`)

Parent: [`../interactive_chat_plan.md`](../interactive_chat_plan.md) §8.5, §15
Depends on: nothing. **Ship this independently of all chat work.**
Blocks: M9.3's licence gate, and any licensed (non-public-domain) content import
Effort: 1 day

## Why this ships first and alone

A licensed Bulgarian text is expected soon. The flag that says whether a work's text may be sent to an external AI service must exist **before** that import, not after — otherwise the work lands with no policy and the only safe reading of a missing flag is to block it.

It is also the *only* server-side change in the whole M9 programme. Shipping it on its own means the schema bump, the content rebuild and the deploy ordering are exercised in isolation, instead of inside an 8-day frontend milestone where a `503 schema-outdated` would be confusing.

## The change in one sentence

Add `works.ai_context_policy` (`allowed` | `prohibited` | `unknown`), populated by the importer, exposed read-only through `GET /api/v1/works` and `GET /api/v1/books`, and typed in the web client.

Data flows **outward only**: importer → `content.sqlite` → API → browser. Nothing is sent to the server. The server stays read-only and stateless.

## Design decisions already made — do not re-litigate

- **The dataclass field has no default.** Every `WorkMeta(...)` construction site must state the policy explicitly. A licence gate whose value can be silently omitted is the exact failure this guards against; a missing value should break the build, not default quietly.
- **The SQL column and the API model both default to `"unknown"`**, and `unknown` behaves as `prohibited` at the point of use. That is belt-and-braces for a row written by something other than the current pipeline.
- **The CLI argument is required.** A new work imported through `build-bible` cannot be created without stating its policy.
- This is *not* a security boundary against a determined user — the browser makes the outbound call and a user can edit their own client. Its value is that policy travels with the content it describes and is versioned with it.

## Files to change

```python

```

In `CREATE TABLE works` (line ~20), after `source_version`:

```sql
    ai_context_policy TEXT NOT NULL DEFAULT 'unknown'
        CHECK (ai_context_policy IN ('allowed','prohibited','unknown')),
```

The `CHECK` matters: it makes an invalid value a write-time failure in the offline importer rather than a runtime surprise in the browser.

## Deploy — order is not optional

From `plan/deployment/live-runbook.md`. `ContentSchemaMiddleware` (`apps/api/app/main.py:53`) returns 503 for every `/api/v1` request when `PRAGMA user_version` does not equal `CONTENT_SCHEMA_VERSION`. So:

1. **Rebuild `content.sqlite`** with the new importer, to a temporary path.
2. Verify locally: `PRAGMA user_version` is 3, and every `works` row has a policy.
3. **Atomically rename** the new file into place on the VM.
4. **Restart the API.**
5. Deploy the SPA.
6. Confirm `/ready` returns 200 with `schema_version == expected_schema_version == 3`.

Restarting the API before the rebuilt database is in place makes every `/api/v1` request correctly return `503 schema-outdated` and pages the readiness monitor. There is no partial-availability mode; do not attempt one.

Rollback: put the previous `content.sqlite` back and deploy the previous API image. Both must move together.
