## Scope

Answer open-ended questions — "What does the Bible say about resurrection?" — that name no
reference and therefore select no context chips. One model call turns the question into English
search terms, the browser searches the corpus with them, and the hits become ordinary
`StudySource` records that the existing grounded pipeline answers over.

Everything after "the hits become sources" is M9.3 machinery. This milestone adds a retrieval
front-end to it, plus the staged turn that front-end requires (§7). No server change.

## Decisions (owner interview, 2026-09-04)

| Question | Decision |
|---|---|
| What text is the excerpt for a hit? | **Hybrid.** Bible/dictionary/Strong's hits re-fetch exact content; commentary and General Book hits use the search snippet, cleaned and labelled as an excerpt. §3 |
| What triggers expansion? | **An explicit composer toggle**, off by default. No implicit second model call, ever. §5 |
| Which content types are searched? | **All of them**, with per-group caps. §2 |
| Where do Strong's hits go? | **Reuse existing targets** — `strongs_entry` → a `lexicon` source, `strongs_occurrence` → a `bible` source. No new `SourceKind` or `CanonicalTarget` variants. §3 |
| Expansion call fails or fails validation? | **A typed `expansionFailed` error** offering retry / switch model / send without search. No silent fallback to the raw question. §4 |
| Where are the terms shown? | **A confirm step with editable term chips**, before the search runs. §6 |
| Blocked on M9.0b-2? | **No.** Proceed; assert term quality in M9.4's own tests. §"Tests" |

## Corrections to the parent plan's §10

Four of §10's assumptions do not survive contact with the code. They are corrected here rather
than in `interactive_chat_plan.md` so the parent keeps its record of what was believed at
planning time; §10 and the §4.1 sequence diagram now point here.

**1. Terms cannot share one search call.** §10 says "The browser calls `GET /api/v1/search` …
Nothing else," singular, and §4.1's diagram draws exactly one. But `fts_query()`
(`apps/api/app/search_providers.py:39`) builds an **AND of quoted tokens** — no OR is reachable
from the API, and `refine` is ANDed too. A single call carrying `resurrection raised risen`
matches only documents holding all three, which for a five-term expansion is approximately
nothing. **One multi-type call per term, merged in the browser.** That is 2–5 calls, and it is
the single most consequential fact in this milestone.

**2. There are five search types, not six.** `ALL_TYPES = ("bible", "commentary", "dictionary",
"book", "strongs")` (`search_providers.py:33`). `strongs` is one *type* that emits two *hit
kinds*. "All six types with per-group caps" is answered by five.

**3. "Pagination" is moot, and the per-group cap already exists.** A multi-type query returns
`PREVIEW = 5` rows per group and **ignores `limit`/`offset` entirely** (`routers/search.py:91`).
One multi-type call yields at most 25 hits across 5 groups, already capped per group, with no
paging decision to make. The §15 line "filtered search, pagination" describes work the API does
for us.

**4. `strongs_occurrence` is unreachable on this milestone's request shape.** The strongs
provider returns occurrence hits only when `verse_text` or `morph` is supplied
(`routers/search.py:105`); otherwise it returns entry hits. M9.4 supplies neither. The
occurrence mapper is still written — `SearchHit` is a union and the mapper must be exhaustive —
but it is exercised by its own unit test, not by an end-to-end turn. Do not claim it is covered.

One more, about budgets: §8.3's "8,000 tokens total, 2,000 per source, `max_tokens` 1,500" was
superseded by M9.3c/M9.3d. The live numbers are `DEFAULT_TOTAL_BUDGET = 16000`,
`DEFAULT_PER_SOURCE_CAP = 6000`, `DEFAULT_MAX_ANSWER_TOKENS = 4000`, `MAX_SOURCES = 12`
(`chat/contextBudget.ts`), all reader-configurable. Size every estimate below against those.

## 1. Expansion — `apps/web/src/chat/expand.ts`

New file, named in the parent's §14 layout.

```ts
export interface ExpansionResult {
  terms: string[];        // 2-5, validated
  usage?: ChatUsage;      // merged into the turn's total (§7)
}

export async function expandQuestion(
  question: string,
  model: ChatModel,
  privacyRouting: boolean,
  signal: AbortSignal,
): Promise<ExpansionResult>;
```

**Reuse `streamChat` (`client.ts:310`); do not add a transport.** Accumulate the deltas into a
string and parse the whole. The point is not streaming — it is that `streamChat` already carries
the typed error classification, the ZDR/`data_collection` privacy routing, the reasoning
suppression, and abort plumbing. A second bespoke fetch path would have to re-earn all four, and
the privacy routing is not optional here: **the expansion call sends the user's question to the
provider**, so it must travel the same constrained route as every other request. It carries no
source text, so the `ai_context_policy` licence gate does not apply to it — say so in the code,
because the asymmetry looks like an oversight otherwise.

`maxTokens: 200`. A term list needing more than that is malformed by definition.

**[R4] `streamChat` retries by itself, and expansion must switch that off.** `MAX_RETRIES = 2`
is a module constant (`client.ts:79`); the loop at `:314` re-issues the request on `rateLimit`,
`network` and `malformedStream` with backoff, and `ChatRequest` offers no way to decline. Left
alone, a failing expansion would make **three** POSTs before the reader sees an error — which
contradicts §4's "no automatic retry" and the cost guarantee behind it, and does so invisibly.
So `ChatRequest` gains one optional field:

```ts
export interface ChatRequest {
  // ...
  maxRetries?: number;   // default MAX_RETRIES (2); expansion passes 0
}
```

honoured as `retries >= (req.maxRetries ?? MAX_RETRIES)`. The default keeps the answering call's
behaviour byte-for-byte, and `expandQuestion` passes `0`. This is a third small change to shipped
code, alongside `buildContext` and `api.search` (§3, §2). The `retries` field `ChatRunMeta`
already reports becomes the assertion: a failed expansion reports `retries: 0` and one POST.

**[R] Abort must be raised explicitly; `streamChat` will not do it for you.** `parseSse` treats
cancellation as a clean end — "cancelled: resolve cleanly, nothing thrown" (`sse.ts:59`) — and
`streamChat` then *returns normally* with `incomplete: true` (`client.ts:306`). That is
deliberate and load-bearing for the answering call, where Stop keeps the partial answer and
flags it. Here it is a trap: a cancelled expansion would hand back a truncated JSON fragment,
fail validation, and surface `expansionFailed` to a user who pressed Cancel. So:

```ts
const meta = await streamChat(...);
if (signal.aborted) throw new ChatError("aborted", "The request was cancelled.");
// only then: strip fence, JSON.parse, validate
```

**Prompt.** Add `buildExpansionMessages(question, uiLang)` to `prompt.ts` alongside
`buildMessages` (`prompt.ts:82`). Its own contract, not the grounded one:

- return **only** a JSON array of 2–5 English search terms, no prose, no code fence;
- terms are single words or short phrases as they would appear in an English Bible,
  commentary, or dictionary — not a restatement of the question;
- the corpus is English; a Bulgarian question still yields English terms;
- the question is data, not instructions.

**Validation, in the browser, before anything is searched.** [R] Strip **one** leading/trailing
markdown fence before `JSON.parse` — models wrap JSON in ` ```json ` routinely despite being told
not to, and unwrapping is still schema validation, not a fallback. Then reject on any of: not an
array; fewer than 2 or more than 5 entries; a non-string entry; an entry outside 2–40 characters;
an entry containing anything but letters, digits, spaces, hyphens and apostrophes.

[R] Digits are allowed deliberately. `_TOKEN = re.compile(r"\w+")` (`search_providers.py:32`)
extracts `\w+` runs and quotes *those*, so a digit run is a clean token and forbidding digits
would reject `1 Corinthians`, `Psalm 23` and `G3439` for no reason. The rule still excludes every
FTS5 operator character (`"` `*` `(` `)` `:` `^`), and the bare words `AND`/`OR`/`NOT`/`NEAR` are
inert once each token is quoted. Defence in depth: the server sanitizes too, and neither layer is
permitted to rely on the other.

[R5] **Apostrophes and hyphens are accepted by the validator but split by the tokenizer**, and
the first draft claimed the opposite for apostrophes. `'` is not `\w`, so `Lord's` becomes
`"Lord" AND "s"`. The review that caught this proposed stripping the apostrophe to `Lords`;
**measured against the project's own tokenizer, that is the wrong fix.** Every FTS table uses
`unicode61 remove_diacritics 2` (`schema.py:244`–`:257`), and unicode61 treats `'` as a separator
at *index* time too — so "Lord's" is indexed as the two tokens `lord` and `s`. Against an in-memory
FTS5 table with that tokenizer holding `the Lord's prayer`:

| query | matches |
|---|---:|
| `"Lord" "s"` — what `fts_query` produces today | **1** |
| `"Lord"` | 1 |
| `"Lords"` — the proposed strip | **0** |

So the split is not a bug: the query and the index disagree in the same way and therefore agree.
Stripping to `Lords` would break a term that currently works. **Leave apostrophes to the
tokenizer; do not normalize them.** The one-letter `s` token costs some precision — it is present
in every possessive — but the AND with `lord` bounds it. The same holds for hyphens
(`self-control` → `"self" AND "control"`, indexed the same way). Document the behaviour; change
nothing. And do not use `Lord's` as an example of a term that searches *cleanly*; it is an
example of a term the validator must not reject.

Trim and casefold-dedupe. There is no joined-length concern: each term is its own `q` under 40
characters, far inside the server's `max_length=200`.

## 2. Search fan-out — `expand.ts`

```ts
export async function searchTerms(
  terms: string[],
  signal: AbortSignal,
): Promise<RankedHit[]>;   // { hit: SearchHit; workId: string; term: string; rank: number }
```

One `api.search(term, { sort: "relevance" })` per term — no `types` filter, so all five groups
come back at `PREVIEW = 5` each. No `limit`, no `offset`: multi-type ignores both (§Corrections 3).

Issue the calls **in parallel** (`Promise.all`). They are independent GETs against a read-only
API and the fan-out is at most five.

**[R] `api.search` must learn `signal` first.** `get()` already forwards a `RequestInit`
(`data/api.ts:343`) and `api.passage`/`api.commentary` pass `{ signal }`, but `api.search`
(`data/api.ts:420`) takes `q` and opts only. Without this, a `Promise.all` of unabortable GETs
outlives Stop and Cancel, and §7's "no pending fetch" is unenforceable. Add `signal?:
AbortSignal` in the same shape as `api.passage`. Map a fetch `AbortError` to
`ChatError("aborted")` — never to `expansionFailed` or `network`.

**Merge round-robin across terms, not by concatenation.** Take rank 0 of every term, then rank 1
of every term, and so on. Concatenating puts all of term 1's hits first, and when the candidate
cap bites, terms 3–5 contribute nothing — the expansion would be decorative for most of the
terms it showed the user. Within one rank, keep the group order the API returned.

**[R] Dedupe on a key the canonical target does not carry.** Keying the merge on
`canonicalTarget` collapses distinct commentary hits: `CanonicalTarget.commentary` is
`{ kind, workId, osis, chapter }` (`types.ts:15`) with no verse, so a Matthew Henry hit on
1 Cor 15:4 and another on 15:12 are byte-identical targets. Verse-scoped entries are the common
MHC case and a topical question will routinely hit several in one chapter. Key on the hit's own
discriminator instead — **always qualified by `kind` and `work_id`**, because [R5] every one of
those discriminators is per-work, not global: `commentary_entries` is
`PRIMARY KEY (work_id, entry_id)` (`schema.py:110`), and the comment above it says outright that
two commentaries "can both number from 1 without colliding"; `book_sections` is
`(work_id, section_id)` (`:187`); a verse ref is shared by every Bible work. Search runs across all
types with no work filter, so a merge keyed on the bare id would drop a real hit from a second
work as a "duplicate" of the first. `RankedHit` already carries `workId`. The keys:

```ts
bible:      `bible:${workId}:${osis}:${chapter}:${verse}`
commentary: `commentary:${workId}:${entry_id}`
dictionary: `dictionary:${workId}:${headword}`
book:       `book:${workId}:${section_id}`
lexicon:    `lexicon:${strong_id}`            // Strong's ids are global by construction
```

`isDuplicate` in `buildContext` is already safe here — it compares `workId` before anything else —
so the merge step is the only place this can throw sources away. §3 carries the *coverage* fix
(`entryIds`) into `buildContext` for chip-versus-excerpt dedupe; that is a different question from
this one and `entryIds` is not the merge key.

**Cap the merged list at 16 candidates.** Why 16 against `MAX_SOURCES = 12`: `buildContext` will
drop some for licence, cap, dedupe against the user's own chips, and budget, so headroom is
right — but each surviving Path A candidate costs one API fetch inside `buildContext`, and **that
loop is sequential** (`context.ts:400`, `for … await`). 16 is where the headroom stops paying for
the latency. Do not raise it without measuring, and do not parallelize that loop here — it is
shipped M9.3 code serving every other turn, and changing it belongs in its own change.

## 3. Hits → candidates

Two paths, which is exactly the hybrid decision.

**Path A — hits that become ordinary `ContextChip`s.** These need no new machinery, because each
of these hit kinds already has a chip that fetches precisely the right unit:

| Hit | Chip | What gets fetched |
|---|---|---|
| `BibleHit` | `{ kind: "bible", workId, osis, chapter, verses: String(verse) }` | the exact verse, ~30 tokens — not the chapter |
| `DictionaryHit` | `{ kind: "dictionary", workId, headword }` | the full entry; Easton's median is 151 tokens |
| `StrongsEntryHit` | `{ kind: "lexicon", strongId }` | the real lexicon entry via `api.lexiconEntry` |
| `StrongsOccurrenceHit` | `{ kind: "bible", workId, osis, chapter, verses: String(verse) }` | the exact verse (see §Corrections 4) |

Append these to the `chips` array `ChatPanel` passes to `buildContext`. The `verses` field is
what makes "exact verse, never the whole chapter" fall out of existing code rather than needing
new code — the same rule §8.2 states for the reader.

**Path B — hits that carry their snippet.** `CommentaryHit` and `BookHit` only. Fetching these
for real would be correct and unaffordable: Matthew Henry's median verse-scoped entry is 3,593
tokens (M9.3c's measurement), so a dozen is 43,000 against a 16,000 budget, and eight of the
twelve would be dropped as `budget` *after* being fetched.

**[R] The snippet is FTS markup, not text — clean it before it becomes an excerpt.** Every
provider builds its snippet as `snippet(…, '<b>', '</b>', '…', 12)`
(`search_providers.py:192` for commentary, `:270` for books). The search UI already knows this
and has a dedicated `Snippet` component that splits on the markers so React escapes the rest
(`SearchPanel.tsx:62`). Nothing in the chat path does: `ChatSources` renders
`<blockquote>{source.excerpt}</blockquote>` (`ChatSources.tsx:28`) with no HTML renderer, so tags
would appear literally to the reader — and, worse, would enter the prompt, bypassing
`normalize.ts`'s "never emit markup" rule and inviting the model to quote `<b>` as if it were
source text. Labelling a source an "excerpt" covers truncation; it does not cover markup.
**Strip `<b>` and `</b>` — those two literals only, never a general HTML strip — before building
the candidate.**

```ts
// commentary
{
  source: {
    kind: "commentary",
    workId, label,                       // label ends with the excerpt marker
    canonicalTarget: { kind: "commentary", workId, osis, chapter },
    language, excerpt: stripHighlights(hit.snippet),
    estimatedTokens: estimateTokens(stripHighlights(hit.snippet), "commentary"),
  },
  requires: [{ workId, policy: work?.ai_context_policy ?? "unknown" }],
  entryIds: [hit.entry_id],
}

// book — the shape the first draft left implicit
{
  source: {
    kind: "book",
    workId, label,
    canonicalTarget: { kind: "book", workId, sectionId: hit.section_id },
    language, excerpt: stripHighlights(hit.snippet),
    estimatedTokens: estimateTokens(stripHighlights(hit.snippet), "book"),
  },
  requires: [{ workId, policy: work?.ai_context_policy ?? "unknown" }],
  dedupeKey: `book:${workId}:${hit.section_id}`,
}
```

[R] `work?.ai_context_policy ?? "unknown"`, with the optional chain — every chip path in
`context.ts` uses exactly that (`:186`, `:217`, `:241`, `:264`), and a missing work must gate as
`unknown`, not throw.

`CommentaryHit.verse_start` is nullable for chapter introductions and
`CanonicalTarget.commentary` has no verse field, so it is dropped from the target — a citation
opens the chapter, which is where an introduction lives anyway. Put the verse in the human label.

**Labelling, in the source and in the prompt.** The source label carries a marker
(`chat.expansion.excerptMarker`), and the prompt states that a source so marked is a search
excerpt which may begin or end mid-sentence and must not be quoted as a complete statement. This
is the one place M9.4 loosens §8.3's "never truncate a source mid-excerpt", and the loosening is
only defensible while it is visible to both the model and the reader. It does not apply to
scripture: no Bible text reaches the prompt as a snippet, which is the whole reason Path A exists.

**[R] Emit that prompt rule conditionally.** `systemContract()` (`prompt.ts:54`) is unconditional,
so adding the excerpt rule there changes the system message of **every** grounded turn, including
every toggle-off turn — which would break this milestone's own first DoD line by itself. Add the
rule only when at least one source in the manifest carries the marker.

### The changes to shipped M9.3 code — `buildContext`, `isDuplicate` (and `ChatRequest.maxRetries`, §1)

**`buildContext` accepts pre-built candidates.**

```ts
export async function buildContext(
  chips, works, privacyRouting, signal, budget = DEFAULT_CONTEXT_BUDGET,
  extraCandidates: ExtraCandidate[] = [],   // Path B only
)
```

where `ExtraCandidate` is `Candidate` with `source: Omit<StudySource, "id" | "contentVersion">`
plus the coverage fields below (`entryIds` / `dedupeKey`). [R] `contentVersion` is **stamped by `buildContext`** from the
`api.meta()` call it already makes at `context.ts:396` — the first draft asked the caller to
supply it while also forbidding a second `meta()` call, which is not satisfiable. `Candidate`
becomes exported.

Extras are appended to `candidates` after the chip loop; steps 2–7 — licence gate, per-source
cap, kind ranking, dedupe, budget, contiguous id assignment — then apply identically, which is
the entire reason for threading them through this function instead of building sources beside it.
Three properties come free and all three are load-bearing:

- a `prohibited` or `unknown` work's snippet is dropped before it can be sent, exactly like a chip;
- an expansion hit duplicating the user's own chip is dropped as `duplicate`, and because chips
  are appended first, the copy that survives is the user's;
- ids stay contiguous and are still assigned only by `buildContext` — never by the model, and now
  also never by the expansion path.

**[R] `isDuplicate` learns entry coverage, not just a key.** Its non-bible branch is
`JSON.stringify(at) === JSON.stringify(bt)` (`context.ts:383`), which collapses two distinct MHC
entries in one chapter into one 12-word snippet. The first fix was a `dedupeKey` compared when
*both* candidates carry one, falling back to chapter equality otherwise. [R3] That fallback is
the bug in a new place: a reader chip for 1 Cor 15:4 (no key — it came from a chip) against a
search excerpt for 15:12 (keyed on its `entry_id`) falls through to the chapter comparison and the
excerpt is dropped as a duplicate of a source that does not contain it.

The chip path already knows exactly which entries it fetched. `api.commentary` returns
`CommentaryEntry[]` with `entry_id`, `verse_start`, `verse_end` (`data/api.ts:225`), and
`selectCommentaryEntries` (`context.ts:93`) picks the ones covering the chip's verse. So give the
commentary candidate the same shape the bible candidate already has for verses:

```ts
interface Candidate {
  source: Omit<StudySource, "id">;
  requires: RequiredPolicy[];
  verseSpan?: VerseSpan;          // bible: the verses this source actually contains
  entryIds?: number[];            // commentary: the entry_ids this source actually contains
  dedupeKey?: string;             // book / dictionary / lexicon: one discriminator
}
```

The chip path sets `entryIds` to the ids of the entries it concatenated; a Path B commentary
excerpt sets `entryIds: [hit.entry_id]`. Then for two commentary candidates on the same work and
chapter, **duplicate means the entry sets intersect** — precisely parallel to `spansOverlap` for
bible. A chip for 15:4 whose entry spans 1–11 and an excerpt from the entry spanning 12–19 do not
intersect and both survive; an excerpt from the *same* entry the chip already fetched in full is
correctly dropped, and because chips are appended first, the full text wins over the snippet.
Only when *neither* side carries coverage data does today's chapter-equality fallback apply —
which after this change is never, for commentary, and is kept only so the function stays total.

For `book`, `dictionary` and `lexicon` the discriminator is single-valued (`section_id`,
`headword`, `strong_id`) and already *is* the canonical target's identity, so `dedupeKey` is
optional sugar there; the existing `JSON.stringify` comparison is already correct for them.
Navigation stays at chapter granularity — `openCommentary` has nothing finer — but *uniqueness of
sources* must not.

Set `verseSpan` on Path A bible candidates so verse-level dedupe works against the reader's own
chips. `KIND_PRIORITY` (`context.ts:39`) then ranks bible over commentary over lexicon over
dictionary over book, with insertion order breaking ties — so §2's round-robin relevance order is
preserved within each kind. That ordering is correct as-is.

## 4. `expansionFailed` — `apps/web/src/chat/errors.ts`

One new `ChatErrorKind`, with a generic message beside its neighbours in `GENERIC_MESSAGE`:

```ts
| "expansionFailed"  // the model did not return a usable list of search terms
```

**[R] It covers every non-validating outcome, not just a schema miss.** The expansion call can
fail as `emptyAnswer` (mandatory reasoning against `maxTokens: 200` — `client.ts:292`),
`malformedStream`, `badRequest`, or as syntactically fine output that is not a term list. All of
those are one situation from the reader's side: *no terms came back*. Classify them all as
`expansionFailed`, so they all reach the three recovery actions. The exceptions pass through
untouched, because each has its own correct remedy: `aborted`, `auth`, `credit`,
`privacyConstraint`.

Three ways out, offered in the UI: **retry**, **switch model**, and **send without search**. The
third re-sends the same question through the ordinary M9.3 path — a real answer over the user's
own chips rather than a dead end.

[R5] **Send-without-search bypasses the §7a empty gate, by construction.** It is a one-shot
`forceAnswer` on the in-flight question: skip expansion, skip search, run `buildContext` over the
reader's chips (typically none, for a topical question), and call `streamChat` with whatever that
returns — **including an empty manifest**. The gate in §7a exists to stop an *accidental*
ungrounded turn; this action is the reader choosing one deliberately, after being told the search
produced nothing, and it must not be routed back into the gate it is the exit from. Without this
the action is unreachable from `expansionFailed`, where no terms exist yet and `empty`'s copy
("the terms that were tried") has nothing to list, and it loops from `empty` itself.

[R] "Send without search" is a **one-shot skip of the in-flight question**, not a flick of the
session toggle (§5). Using the session control as the bypass would silently disable search for
every later turn, which is not what the action means.

**No fallback to the raw question as a search term.** It looks like graceful degradation and is
not: a Bulgarian question run as an FTS query against an English corpus returns zero hits, so the
model would receive an empty source set and answer from recall — the exact failure this milestone
exists to prevent — while the UI showed a completed turn. An error the reader can act on beats an
answer they cannot trust.

No automatic retry — neither a re-prompt nor the transport's own. A re-prompt is a third billable
call on a turn already going badly; the transport's built-in two retries would be the same thing
one layer down, and §1 switches them off for this call with `maxRetries: 0`. The user's own Retry
is one click.

## 7. The staged turn — `components/chat/ChatPanel.tsx`

**[R] This is the section the first draft got wrong, and it is why the estimate moved.** `send()`
is not a body that can be branch-prefixed. Before it ever reaches `buildContext` it clears the
composer, appends an empty assistant message, sets `streaming` (flipping Send to Stop), and
persists the user message (`ChatPanel.tsx:284`–`:315`). Prepending an expansion branch would
render the confirm panel over a blank assistant bubble; Cancel through the existing abort path
keeps that bubble, because the `catch` at `:440` preserves `prev` on abort; and neither Retry nor
"send without search" could re-enter, since `canSend` requires `input.trim().length > 0` and the
input was emptied at the top. There is also **no Retry control in the app today** — it is new UI,
not a reuse.

**[R2] And "delay the assistant row" is not enough on its own** — the second review caught that
the first rewrite removed the row without replacing what the row *owns*. Three things hang off
`assistantId` today and would have nowhere to go: every non-abort error is attached to it
(`:440`) and rendered only there (`:483`), so `expansionFailed` and its three actions would have
no mount point; `streaming` is the sole Send↔Stop switch (`:631`), so tying it to the delayed row
leaves expansion and the fan-out with no cancel control, while setting it at capture shows Stop
*and* Cancel during confirm; and the confirm step is an `await` in the middle of `send()`, which
`AbortController.abort()` does nothing to — it rejects fetches, not arbitrary promises — so Stop
or Escape could leave `send()` hung forever with the composer already cleared.

So the turn becomes an explicit **phase machine**, not a later insert:

```ts
type TurnPhase =
  | { kind: "idle" }
  | { kind: "expanding";  question: string }
  | { kind: "confirm";    question: string; terms: string[] }
  | { kind: "searching";  question: string; terms: string[] }
  | { kind: "streaming";  question: string }            // today's behaviour, unchanged
  | { kind: "empty";      question: string; terms: string[] }   // §7a — post-search only
  | { kind: "error";      question: string; error: ChatErrorKind; terms?: string[] };
```

held in `ChatPanel` state alongside `messages`. The `question` travels in the phase from capture
onward: it is the single source for Retry, edit-terms, and send-without-search, and it is what
gets restored to the composer on cancel.

**What happens in each phase.**

| Phase | Cancel affordance | Where errors go | Rows that exist |
|---|---|---|---|
| `expanding` | **Stop** — aborts the expansion fetch | `phase.error` | none |
| `confirm` | **Cancel** button / Escape (`stopPropagation`, §6). No Stop. | — | none |
| `searching` | **Stop** — aborts every `api.search` via the shared signal | `phase.error` | none |
| `streaming` | **Stop** — keeps the partial answer, flags it incomplete, persists the run | `assistantId`, as today | user + assistant |
| `empty` / `error` | rendered as a turn-level panel above the composer; **every** kind offers Cancel and Retry (§7 table) | `phase.error` | none |

**Rows are created only when the answering call starts.** Neither the user row nor the assistant
row exists — in React state *or* in Dexie — until the machine enters `streaming`. A pre-stream
cancel therefore has nothing to remove: it sets `phase` back to `idle` and **restores `question`
to the composer**, so the reader's text is never lost. A toggle-off turn passes through none of
the pre-stream phases and is indistinguishable from today.

This changes the order of two things M9.3 does at the top of `send()`, and both are safe:

- **The user message is saved later.** Today it is saved before `buildContext` so the pre-send
  summary has a row to upsert onto (`history.ts:33`, the comment on `contextSummary`). Under the
  phase machine `buildContext` has already resolved by the time `streaming` is entered, so the
  user row is written once, complete, with its summary — one put instead of two.
- **[R2] `priorHistory` is captured from `messages` before the turn starts**, exactly as it is
  now (`:296`), and carried in a ref for the turn. It must not be recomputed after the rows are
  added, or the in-flight question would be replayed to the model twice.

**The confirm wait is abortable by construction.** Model it as a promise the phase resolves —
`confirm` stores a resolver; the Search button resolves it with the edited terms, Cancel/Escape
resolve it with `null`, and the turn's `signal` gets an `abort` listener that also resolves
`null`. `send()` awaits that promise and treats `null` as a clean cancel. Nothing in this path
can hang.

**Cancel and Stop are not the same thing, and must not be unified.** One `AbortController` per
turn, as now, but two behaviours:

- **Pre-stream** (`expanding`, `confirm`, `searching`): no rows exist, nothing is saved, the
  question returns to the composer.
- **During `streaming`**: today's shipped behaviour is preserved exactly — the partial answer is
  kept, flagged incomplete, and the run persisted (`ChatPanel.test.tsx:248`, parent §13 "Keep a
  partially streamed answer"). It is a feature, and the first draft's "no orphan at all four
  stages" would have regressed it.

**[R3] Send↔Stop, and a separate active-turn guard.** The first phase-machine draft said to
derive the button from the phase and let `streaming` become `phase.kind === "streaming"`. That
narrows a flag other things depend on. `streaming` currently guards **five** consumers
(`ChatPanel.tsx:241`, `:546`, `:603`, `:614`, `:631`): `canSend`, the composer's disabled state,
Clear-this-thread, Clear-all, and the Send/Stop switch. The comment at `:591` says why the two
history buttons are gated: `send()`'s in-flight closure holds `currentThreadId` and will write
the assistant message and run under it when the turn finishes, so clearing mid-turn resurrects
the thread as orphaned rows visible in a later Export JSON. If `streaming` is false during
`expanding`/`confirm`/`searching`, a reader can clear history at the confirm step and the
pending turn will then write under a deleted thread — and, because `priorHistory` was captured
pre-turn, replay messages the reader believes are gone.

So there are two flags, with different jobs:

```ts
const turnActive = phase.kind !== "idle";                    // any turn in flight, any phase
const streaming  = phase.kind === "streaming";               // the answering call specifically
```

- **`turnActive`** replaces `streaming` in `canSend`, the composer's `disabled`, Clear-this-thread
  and Clear-all. A turn in any non-idle phase blocks all four. Retry / edit-terms / send-without-
  search are the *only* ways to act while `turnActive`, and they belong to the phase panel.
- **`streaming`** keeps its name and its single remaining job — the Stop-keeps-the-partial-answer
  behaviour and the tests that assert on it.
- The **Send/Stop button** derives from the phase: Stop in `expanding`, `searching`, `streaming`;
  Send in `idle`; hidden in `confirm`, `empty`, `error`, where the panel's own actions are the
  controls.

Update every consumer in the same change as the phase machine, and add a test: Clear-all is
disabled at the confirm step.

**[R3] Every error phase has an exit; `expansionFailed` merely has more of them.** The earlier
draft specified recovery actions only for `expansionFailed`, while hiding Send and Stop in every
error phase — so an `auth`, `privacyConstraint` or `network` failure during expansion or the
fan-out would have stranded the turn with no control on screen, even after the reader fixed the
key or the connection. Define the transitions for the whole `ChatErrorKind` set:

| Error during `expanding` / `searching` | Actions on the panel |
|---|---|
| `expansionFailed` | **Retry** · **Switch model** · **Send without search** · **Cancel** |
| `auth`, `credit` | **Open settings** (fix the key / top up) · **Retry** · **Cancel** |
| `privacyConstraint`, `modelUnavailable` | **Switch model** · **Retry** · **Cancel** |
| `rateLimit` | **Retry** (with the `retryAfterSeconds` countdown the kind already carries) · **Cancel** |
| `network`, `malformedStream`, `badRequest`, `emptyAnswer` | **Retry** · **Cancel** |

Every row has **Cancel**, which returns to `idle` and restores the question to the composer, and
every row has **Retry**, which re-enters the phase that failed with the same `question` (and, for
a `searching` failure, the same confirmed `terms` — the reader should not have to re-confirm terms
because the network blinked). "Switch model" opens the picker and leaves the phase in `error`, so
Retry is one click after choosing. Errors during `streaming` are unchanged: they attach to
`assistantId` as today, since the row exists by then.

### 7a. Zero hits is a normal outcome, and must not become an ungrounded answer

**[R2]** Weak terms, an English query that misses the corpus, or a merged list whose every hit
`buildContext` drops for licence — all produce an **empty expansion manifest**. Running the
answering call anyway sends the model the question with no sources, it answers from recall, and
the UI shows a completed, term-labelled search. That is byte-for-byte the failure §4 forbids for
the raw-question fallback, arriving by a different door.

Gate on the **complete manifest `buildContext` returns**, not on the raw hit list and not on the
reader's selected chips. [R3] The first draft of this section said "proceed if the reader has
chips", but a chip is a *request*, not a source: `buildContext` drops chips too — for licence,
for the per-source cap (a whole-chapter commentary chip is over 6,000 tokens 92% of the time,
M9.3c), for `unavailable` content. A reader with three chips can arrive at an empty manifest, and
an empty manifest is an ungrounded turn whichever door it came through. [R5] The rule has one
input and one exemption: it runs **only on the post-search path** — `searching → buildContext` —
and never on a turn carrying `forceAnswer` (§4), which is the reader's explicit choice to answer
ungrounded. A toggle-off turn is not gated either; it is M9.3's turn and behaves as today.

- **`sources.length === 0`** → enter `empty`. Do not start the answering call. The panel says
  nothing usable was found, lists the terms that were tried, and — reading `dropped` — says
  whether that is because the search matched nothing, because matches were found but none may be
  sent (licence), or because the reader's own chips were dropped (over-cap, unavailable). It
  offers **edit terms** (back to `confirm` with the same list), **retry expansion**, and the
  one-shot **send without search** — which sets `forceAnswer`, so it goes straight to `streamChat`
  over the current (empty) manifest rather than re-running `buildContext` into this gate again.
- **`sources.length > 0` but no source came from expansion** → proceed. The turn is grounded by
  the reader's chips. Add a line to the pre-send summary and the terms row saying the search
  contributed nothing, so the terms shown are not read as the answer's evidence.
- **At least one expansion source survived** → proceed as normal.

The distinction between "zero hits" and "hits that were all dropped" is visible in the
`dropped` list `buildContext` already returns, so the empty-state panel can say which one
happened — "nothing matched" and "matches were found but none may be sent" call for different
next actions.

**Usage must be summed, not overwritten.** `onMeta` does `usage: partial.usage ?? m.usage`
(`ChatPanel.tsx:398`) and `saveRun` writes `usage: meta.usage` (`:434`), so a second `streamChat`
replaces the expansion's usage rather than adding to it — and a reader who sees one answer would
be shown half the tokens they paid for. Add a `mergeUsage(a, b)` helper summing `promptTokens`,
`completionTokens`, `totalTokens`, `reasoningTokens` and `cost` (all optional numbers,
`client.ts:45`), keeping `isByok` from the answering call. Carry the expansion's usage in the
phase until the answering call's arrives, then write the merged object to both the message and
the `ChatRun`. `actualModel` reports the answering call; when the router resolved the two calls to
different models, record both (§8).

**One assistant message per turn.** The expansion is a step within the turn, not a message.

With the toggle off, the machine goes `idle → streaming` in one step, not one line of the
expansion path executes, and the request is byte-for-byte what M9.3 sends today. Assert that
against a recorded fixture, not merely against "the branch was skipped".

## 8. History — `chat/history.ts`

`ChatRun` (`history.ts:42`) gains two optional fields:

```ts
expansionTerms?: string[];       // what was actually searched, after the user's edits
expansionModel?: string;         // when the router answered the two calls with different models
```

Optional, so no Dexie version bump: `ChatHistoryDB` is at `version(1)` with `runs: "messageId"`
and neither field is indexed. A turn from before M9.4 simply has none.

**[R] Terms are metadata and must never be baked into the message text.** Two reasons. The
history loader copies only `finishReason`, `actualModel`, `usage` and the manifest onto the
restored message (`ChatPanel.tsx:148`), so a terms row rendered from `text` would survive reload
only by accident of being inside the string. And `priorHistory` replays assistant `text` verbatim
on the next turn (`ChatPanel.tsx:296`), where `stripCitationMarkers` would not remove it — the
model would receive its own terms row as if it had written it. Add `expansionTerms` to
`DisplayMessage`, render it in the assistant chrome, and restore it in the loader alongside the
other run fields.

The terms stored are the **confirmed** ones, not the model's proposal — history must record what
was searched, not what was suggested. Private sessions store nothing, as now.
