### 1a. Anthropic — the browser header is exactly the mechanism

Proven in both directions.

- With the header: `access-control-allow-origin: *` on the preflight; browser reads the response.
- Without it: preflight returns HTTP 400 and **no** `access-control-allow-origin`; browser reports "No 'Access-Control-Allow-Origin' header is present" and `fetch` throws.

The preflight must also declare the header in `Access-Control-Request-Headers`, which the browser does automatically. A curl test that omits it will wrongly look like a failure.

**Resolves the open question in `m9.2-workspace-and-provider.md` §1:** `GET /v1/models` works through the OpenAI-compatibility layer with `Authorization: Bearer`. The dummy-key response is `{"type":"error","error":{"type":"authentication_error","message":"Invalid bearer token"}}` — the endpoint accepted the auth *scheme* and rejected only the token's validity. **No static model list is needed.** Confirm once with a valid key.

### 1b. Gemini — works, contrary to the plan's assumption

`https://generativelanguage.googleapis.com/v1beta/openai` responds to a browser `POST /chat/completions` with a readable HTTP 400 (`"Please pass a valid API key"`), and the preflight from `https://bible.trendafilovi.net` returns `access-control-allow-origin: https://bible.trendafilovi.net`.

`Authorization: Bearer` is accepted — the error concerns key *validity*, not the auth method. **A key in the URL is not required**, so the §4.2 rule against credentials in URLs is not violated.

The plan marked Gemini "gated on the spike, undocumented". It is now cleared, with the caveat that this behaviour is still undocumented by Google and could change without notice. Keep the provider registry row easy to remove.

### 1c. OpenAI — the interesting failure

The plan said `api.openai.com` "sends no CORS headers". That is **not accurate**, and the real behaviour is a trap:

| Request | Result |
|---|---|
| `OPTIONS /v1/chat/completions` preflight | HTTP 200 with `access-control-allow-origin` **echoing the requesting origin** — both `https://bible.trendafilovi.net` and `http://localhost:8080` |
| The actual `POST /v1/chat/completions` | HTTP 401 with **no** `access-control-allow-origin` header |
| Browser outcome | Blocked. `Failed to fetch`, "No 'Access-Control-Allow-Origin' header is present on the requested resource" |
| `GET /v1/models` from a browser | **Works** — readable 401 |

OpenAI's CORS support is endpoint-inconsistent: the preflight handler answers, the completions response does not carry the header, and the models endpoint does.

**Consequence for anyone re-testing this:** a curl preflight check alone reports success and is wrong. Verify with a real browser request that reads the response body. The conclusion stands — OpenAI direct is unusable — but the reason is narrower than "no CORS at all", and someone will re-open this if the reason is recorded imprecisely.

OpenAI models remain reachable through OpenRouter.

            https://openrouter.ai https://api.anthropic.com

After adding the origins, all four requests went out and the CSP violation list was empty. The CSP is genuinely enforced and is the control.

## 3. Privacy branch — RESOLVED, with a caveat the table did not anticipate

Measured with a real OpenRouter key, `max_tokens: 5`:

| Model | plain | `{provider: {zdr: true, data_collection: "deny"}}` |
|---|---|---|
| `openrouter/free` | OK | **OK** |
| `google/gemma-4-31b-it:free` | OK | HTTP 404 — *"No endpoints found matching your data policy (Zero data retention)"* |
| `nvidia/nemotron-nano-9b-v2:free` | OK | HTTP 404 — same |
| `google/gemini-2.5-flash-lite` (paid) | OK | **OK** |

**Row 1 of the work-order table is ticked: a free option satisfies ZDR + `data_collection: deny`.** The privacy constraint does not have to be weakened.

Two things the branch table did not foresee:

1. **Only the *router* passes; most individually named free models do not.** `openrouter/free` filters to endpoints matching the policy, so it succeeds where its own constituents fail. The model picker must therefore expect a user to select a named free model and receive a 404 — this is exactly what the `privacyConstraint` error kind in `m9.2-workspace-and-provider.md` §5 is for, and it now has a real, common trigger rather than a theoretical one.
2. **Privacy and usability are different axes.** `openrouter/free` satisfies the privacy constraint and is still a poor default for this app — see §7.

## 7. Free-model output quality — a new problem

Four identical Bulgarian requests to `openrouter/free` routed to **four different models**, with very different results:

| Routed to | finish | Content | Assessment |
|---|---|---|---|
| `nvidia/nemotron-nano-12b-v2-vl:free` | stop | 366 chars | **Gibberish Bulgarian.** Grammatically broken, theologically meaningless |
| `nvidia/nemotron-3.5-content-safety:free` | length | `"User"` | A **content-safety classifier**, not a chat model. Unusable |
| `nvidia/nemotron-3-super-120b-a12b:free` | stop | 148 chars | Mostly correct Bulgarian, minor agreement errors |
| `cohere/north-mini-code:free` | stop | 119 chars | Accurate, idiomatic Bulgarian |

Two of four responses were unusable, and one came from a model that is not a general chat model at all. The router advertises capability filtering, but nothing filters for *language quality*.

**How strong is this evidence?** Weak, and it should be read as such. It is four runs of **one** prompt, scored by eye, and **the outputs were not saved** — only the assessments above survive. It is enough to prove that `openrouter/free` is not dependably usable in Bulgarian. It is not enough to rank candidates or to choose a default.

### 7a. Decision: ship no default model

Taken 2026-07-29 by the owner. This **overrides row 1 of the work order's decision table**, which said a free model passing ZDR + `data_collection: deny` should be shipped as the default.

The table's premise was that passing the privacy gate is sufficient. §7 shows it is necessary but not sufficient: `openrouter/free` passes the gate and still produced unusable Bulgarian in half the samples. Shipping it as default would mean a first-time user's first question has roughly even odds of returning gibberish, which reads as "this app is broken", not "free models vary".

Consequences for M9.2:

- The model picker opens with **no selection**, and the Assistant cannot send until the user picks one.
- The picker states the quality caveat plainly, in both languages, and does not present free models as the recommended path.
- The privacy-routing toggle stays on by default and is orthogonal to this.

The decision is revisited when a reproducible benchmark exists — see [`m9.0b-bulgarian-benchmark.md`](m9.0b-bulgarian-benchmark.md), which is small, does not block M9.2's shell work, and must land before M9.3 exits.

## 8. Reasoning and thinking budgets — would have shipped broken

**Both providers silently spend the output budget on hidden reasoning.**

OpenRouter, `openrouter/free`, `max_tokens: 160`: the first run returned **160 chunks and an empty answer** — `finish_reason: "length"`, `completion_tokens: 160`, `reasoning_tokens: 188`, `content: ""`. Fourteen seconds of streaming, nothing to show.

| Request | Result |
|---|---|
| default | Varies by routed model; empty content whenever a reasoning model is picked |
| `reasoning: {exclude: true}` | **Does not help.** 173 reasoning tokens still consumed, content `"User"` (4 chars). `exclude` only hides the output; the budget is still spent |
| `reasoning: {enabled: false}` | **Works.** `reasoning_tokens: 0`, `finish_reason: "stop"`, full content within budget |
| `max_tokens: 1500` | Also works, but wastes tokens and latency on discarded reasoning |

Gemini has the same problem in a different shape: `gemini-2.5-flash` with `max_tokens: 120` returned `finish_reason: "length"`, `completion_tokens: 4`, and 14 characters of a truncated sentence — thinking consumed the rest.

**Consequences for M9.2:**

- Send `reasoning: {enabled: false}` on OpenRouter. Not `exclude`.
- Gemini needs its thinking budget disabled too — but **only some Gemini models can do this at all**. See §8a; this is not a per-provider constant.
- The SSE parser must recognise and **discard** `delta.reasoning` and `delta.reasoning_details`. Their presence was confirmed empirically: the 1500-token run reported `deltaKeys: ["content","role","reasoning","reasoning_details"]` with 437 characters of reasoning. The plan forbids storing chain-of-thought (§12), so the parser must actively drop these, not merely ignore them.
- Treat `finish_reason: "length"` with empty content as a distinct, explainable error, not a blank answer.

### 8a. Reasoning suppression is per **model**, not per provider — documented, not measured

The finding above was measured. The following is from vendor documentation, and it contradicts the shape `m9.2-workspace-and-provider.md` §1 gives the registry (`suppressReasoning(body)`, one function per provider).

**Gemini.** Google's OpenAI-compatibility page states: *"If you want to disable thinking, you can set `reasoning_effort` to `"none"` for 2.5 models"* — and, explicitly, *"Reasoning cannot be turned off for Gemini 2.5 Pro or 3 models."* So:

| Model | Can thinking be disabled? |
|---|---|
| Gemini 2.5 Flash, 2.5 Flash-Lite | Yes — `reasoning_effort: "none"` |
| Gemini 2.5 **Pro** | **No** |
| Gemini 3.x (any) | **No** |

`extra_body.thinking_config` offers `thinking_level` (low/medium/high) and `include_thoughts`, but no "off" — it narrows the budget, it does not remove it.

**OpenRouter** exposes the same thing as per-model metadata on `GET /api/v1/models`, under a `reasoning` object: `mandatory`, `supported_efforts`, `default_effort`, `default_enabled`, `supports_max_tokens`. The docs say of `mandatory`: *"When `true`, hide disable controls and do not send `effort: "none"` — the model rejects it."*

Two consequences the plan does not currently handle:

1. **A capability check must gate the suppression**, not a provider check. Sending the disable flag to a mandatory-reasoning model is rejected by the model.
2. **Dynamic routers omit the `reasoning` field entirely** from their metadata — `openrouter/free` included. So "no metadata" cannot mean "reasoning can be disabled" *or* "cannot"; it is unknown until the answer streams. This is not a contradiction of §8, where `reasoning: {enabled: false}` did work on `openrouter/free` — it means that behaviour is unverifiable in advance and must degrade gracefully rather than be assumed.

**Therefore, for any model where reasoning cannot be disabled**, the only remaining defence is budget: raise `max_tokens` well above the answer length so thinking cannot consume all of it, and keep the `emptyAnswer` error for when it still does. Do not silently send a disable flag that will be rejected.

**Gemini's `total_tokens` does not equal `prompt + completion`** — a run reported `prompt 20 + completion 4` but `total 136`. Hidden thinking tokens are billed in `total_tokens` only. Any cost display must use `total_tokens`, or it will under-report by an order of magnitude. `ChatRunMeta.usage` in `m9.2-workspace-and-provider.md` §4 must therefore carry `totalTokens`.

## 5. Estimator calibration — PARTIAL, and short of its own exit criterion

**Methodology note, because the first attempt was invalid.** Calibrating against `openrouter/free` produced ratios between 0.06 and 1.52 and two samples with no usage at all — because the router picks a different model, and therefore a different tokenizer, on every call. One sample reported 501 prompt tokens for an 86-character string. **Calibration must use pinned models.** Redone against three pinned models; two returned usable data and agree closely.

Measured `chars / prompt_tokens`:

| Sample | chars | ASCII | non-ASCII | `gemini-2.5-flash-lite` (via OpenRouter) | `gemini-2.5-flash` (direct) |
|---|---:|---:|---:|---:|---:|
| en-bible | 241 | 241 | 0 | 4.38 | 4.30 |
| en-commentary | 232 | 232 | 0 | 4.14 | 4.07 |
| **en-lexicon** | 86 | 85 | 1 | **2.21** | **2.15** |
| bg-question | 136 | 24 | 112 | 3.09 | 3.02 |
| bg-plus-en | 128 | 71 | 57 | 3.20 | 3.12 |
| bg-long | 244 | 46 | 198 | 3.25 | 3.21 |

The two models agree to within 3%, so the numbers are trustworthy for this tokenizer family.

**The plan's placeholder heuristic was wrong in both directions:**

- ASCII divisor 3.6 vs measured 4.07 worst case → over-estimates ordinary English prose.
- Non-ASCII divisor 1.8 vs measured 3.02 → over-estimates Bulgarian by ~68%. Cyrillic tokenizes *far* better than the plan assumed; the "roughly 2× worse than ASCII" claim is false — it is about 1.35× worse.
- **But `en-lexicon` tokenizes at 2.15 chars/token**, nearly twice as dense as prose, despite being almost pure ASCII. Dense symbolic text — Strong's ids, abbreviations, punctuation — breaks any single ASCII divisor.

### Recommended implementation

A single global divisor cannot be safe for lexicon entries without doubling the estimate for prose and halving the usable context budget. Use **per-kind divisors**, which costs nothing because `StudySource.kind` is already known at estimation time:

```ts
// Calibrated 2026-07-29 against gemini-2.5-flash and gemini-2.5-flash-lite
// (plan/chat/m9.0-findings.md §5). Divisors are below the measured worst case;
// the 1.15 multiplier covers other tokenizer families.
const DIVISORS = {
  dense: { ascii: 2.0, other: 2.5 },   // kind === "lexicon": Strong's ids, abbreviations
  prose: { ascii: 3.5, other: 2.5 },   // everything else
};
```

Check against the measurements: prose samples land at 1.3–1.5× the true count (safe, acceptable slack), and `en-lexicon` at 85/2.0 × 1.15 ≈ 49 vs 40 actual (safe).

### 5a. Why this is PARTIAL, not RESOLVED

Three shortfalls against `m9.0-spike.md` Check 5, which asked for **~10** prompts spanning the real mix:

1. **Six samples, not ten.** Missing from the mix the work order named: a Matthew Henry commentary sample in isolation, a Strong's entry distinct from the Easton's-style `en-lexicon` sample, and a cross-reference/TSK sample. `en-lexicon` — the one sample that broke the model, at 2.15 chars/token — is a single data point carrying the entire `dense` divisor.

2. **One tokenizer family.** Both pinned models are Gemini. The 1.15 multiplier that is supposed to cover Llama, Qwen and Cohere is a guess, not a measurement. This is not hypothetical: §9 records that five consecutive `openrouter/free` requests were answered by five different models, spanning NVIDIA Nemotron and Cohere — **the very families the calibration does not cover**. An under-count here silently overruns the 8,000-token context budget in `../interactive_chat_plan.md` §8.3, which is the whole point of the estimator.

3. **The samples were not preserved.** Only the character counts and ratios above survive. The measurement cannot be reproduced or extended without reconstructing the inputs, which is why extending it is a fresh task rather than a re-run.

**Resolution — pick one before M9.3 ships the estimator:**

- **(a) Measure the missing families.** Extend to ~10 samples, preserve them as a checked-in fixture with their `usage.prompt_tokens`, and pin one model each from the Gemini, Llama/Nemotron, Qwen and Cohere families. Folded into [`m9.0b-bulgarian-benchmark.md`](m9.0b-bulgarian-benchmark.md), which needs the same fixture corpus.
- **(b) Constrain the supported set.** Restrict the model picker to families with a measured divisor, and treat anything else as unsupported. Cheaper, but it forecloses `openrouter/free` entirely, since a dynamic router cannot promise a family.

(a) is preferred; (b) is the fallback if the benchmark slips. **Until one is done, treat the divisors below as calibrated for Gemini only** and keep the 1.15 multiplier flagged as an unmeasured allowance in `chat/tokens.ts`.

**Limitation to record in code:** both pinned models are Gemini-family. Other families (Llama, Qwen, Cohere) tokenize Cyrillic differently and were not measured — hence the 1.15 multiplier rather than 1.0. Re-measure if a non-Gemini model becomes the default.

## 9. Streaming, usage and abort

**Streaming works on both providers.** OpenRouter: 160 chunks, 797 ms to first byte. Gemini: streams cleanly once the request body is valid.

**Usage opt-in differs per provider, and the plan's single form is wrong for Gemini:**

| Provider | Opt-in field | Result |
|---|---|---|
| OpenRouter | `usage: { include: true }` | Works. Returns `prompt_tokens`, `completion_tokens`, `total_tokens`, `cost`, `is_byok`, `prompt_tokens_details`, `completion_tokens_details.reasoning_tokens` |
| Gemini | `usage: { include: true }` | **HTTP 400** — `Unknown name "usage": Cannot find field` |
| Gemini | `stream_options: { include_usage: true }` | **Works.** Returns `prompt_tokens`, `completion_tokens`, `total_tokens` |

`usage: {include: true}` is an OpenRouter extension, not standard OpenAI. `ProviderConfig` needs a usage-opt-in strategy field rather than one hard-coded body shape.

**Abort is clean on both.** Two chunks in, `AbortController.abort()`, reader cancelled, **no unhandled rejection** on either provider. The design in `m9.2-workspace-and-provider.md` §3 holds.

**Router substitution is real and frequent.** Every `openrouter/free` request reported a different `model` in its stream than the one requested — five requests, five different models. Displaying the actual answering model (plan §13, §17) is load-bearing, not defensive.

**Anthropic is unverified** for streaming, usage and reasoning, and stays that way — the adapter is deferred (§6). Run these checks if it is ever revived.

## 10. Privacy wording and provider terms — the deliverable the spike skipped

`../interactive_chat_plan.md` §15 required two things of M9.0 that this document did not deliver on its first pass: *"Draft the user-facing privacy wording, per provider"* and *"Recheck provider terms — pricing and retention policies change."* The work order's own definition of done omitted both, which is how they went missing; **that omission is itself a defect in `m9.0-spike.md`.** Done here.

### 10a. Gemini's free tier trains on your content — and this is the sharpest finding in the document

Google's pricing page states the difference in four words per tier:

| Tier | Google's wording |
|---|---|
| Free | *"Content used to improve our products"* |
| Paid | *"Content **not** used to improve our products"* |

This is not a retention nuance. On the free tier, everything a user asks the assistant — and every scripture, commentary and lexicon excerpt the app attaches as context — is training data for Google.

Three consequences, all load-bearing:

1. **The Gemini free tier is incompatible with `ai_context_policy = allowed_no_training`.** M9.3's licence gate must block it, not warn about it. This is the concrete reason that value exists (M9.1).
2. **The privacy-routing toggle cannot cover Gemini.** §5.3 already says Gemini has no per-request privacy control; the tier *is* the control, and the app cannot read which tier a user's key is on. The UI must therefore ask rather than detect.
3. **It is not a reason to drop Gemini.** A paid-tier Gemini key is a legitimate, private option, and `google/gemini-2.5-flash-lite` through OpenRouter passes ZDR + deny outright (§3).

### 10b. Google advises against client-side API keys

Google's API-key guidance recommends against embedding keys in client-side applications and directs production traffic through a backend. The app's posture — a user's own key, in `sessionStorage`, for the tab's lifetime, never bundled or shipped — is materially different from the practice being warned against, and `../interactive_chat_plan.md` §4.2 already forbids the disqualifying variants (key in a URL, key in a build). But the divergence is real and must be stated rather than glossed over, in the same place the Anthropic "dangerous" header is explained (`m9.2-workspace-and-provider.md` §8).

### 10c. Draft per-provider wording

Source text for the i18n keys in M9.2 §9 (`privacyNoteKey`). Both languages; English drafted here, Bulgarian translated at implementation time.

**OpenRouter**

> Your question and the study text attached to it are sent to OpenRouter, which forwards them to whichever model you selected. This app always requests zero data retention and asks OpenRouter not to route to providers that train on your data. Some models cannot satisfy that and will refuse the request rather than run without it — that refusal is the protection working. Your own OpenRouter account settings can allow free endpoints that train on or publish prompts; this app cannot see or override those settings. Use a dedicated key with a spend limit.

**Gemini (Google)**

> Your question and the study text attached to it are sent to Google. **On Google's free tier, Google uses that content to improve its products** — that is Google's published policy for free API usage, and this app cannot change it. On a paid tier, Google states the content is not used to improve its products. This app cannot tell which tier your key is on, so choose Gemini only if you accept the free-tier terms or know your key is billed. Google recommends against using API keys directly from a browser; your key stays in this tab only and is never sent to this app's server, but you should still use a dedicated key with a spend limit.

**Both**

> This app never sends your questions to its own server. The connection is made by your browser, directly to the provider, using your key.

### 10e. What a free Gemini tier actually buys you

Asked because it is the obvious "can I run this for nothing?" path. The answer is yes, within limits, **if** you accept §10a.

**Cost is not the constraint** — Flash-tier models are $0 in and $0 out on the free tier. Request quota is. And Google no longer publishes those numbers in its docs: the rate-limits page defers to the per-account page at `aistudio.google.com/rate-limit`, so **the only authoritative figure is the one on your own account**. Widely reported free-tier figures, unofficial and worth treating as an order of magnitude rather than a promise:

| Model | RPM | TPM | RPD |
|---|---:|---:|---:|
| Gemini 2.5 Flash-Lite | 15 | 250,000 | 1,000 |
| Gemini 2.5 Flash | 10 | 250,000 | 250 |
| Gemini 2.5 Pro | 5 | 250,000 | 100 |

Converted into this app's turns, using the budgets in `../interactive_chat_plan.md` §8.3 — 8,000 tokens of assembled context, 1,500 tokens of answer, so **≈9,500 tokens per grounded turn** at the ceiling:

- **Requests per day is what binds.** One question is one request, so ~250 questions/day on 2.5 Flash, ~1,000 on Flash-Lite.
- **Tokens per minute does not bind.** 10 requests/min × 9,500 tokens ≈ 95,000 TPM, comfortably inside 250,000. The per-minute request cap bites first, and 10/min is far above human reading pace.
- **Requests per minute is invisible in practice** for one person reading and asking.
- 2.5 Pro is the wrong choice regardless: lowest quota, and its thinking cannot be disabled (§8a).

**So: on Gemini 2.5 Flash-Lite's free tier, roughly a thousand study questions a day, at zero cost, with Google training on every one of them.** For public-domain content that is a defensible trade the user can make knowingly. For anything marked `allowed_no_training` it is not available at all — the gate blocks it.

Verify against `aistudio.google.com/rate-limit` before quoting any of these numbers in the UI, and do not hard-code them.

## 11. Key validation cannot work as the plan specifies — a design bug found in review

`../interactive_chat_plan.md` §6 step 3 says to validate a pasted key with *"one cheap authenticated call (the provider's models endpoint) so a bad key fails immediately, not mid-answer."*

**For OpenRouter that is impossible**, and §1 of this document is what proves it: `GET /api/v1/models` needs **no authentication** and returns HTTP 200 with 367 models regardless of what is in the `Authorization` header. It is the same property that makes the pre-connect model picker possible. Validation through it therefore accepts any string — including an empty one — and the user learns their key is wrong when their first question fails mid-stream, which is precisely the failure §6 was written to prevent.

**Fix: validation is a per-provider strategy, like usage opt-in.**

| Provider | Validation call | Why |
|---|---|---|
| OpenRouter | `GET https://openrouter.ai/api/v1/key` with `Authorization: Bearer <key>` | Documented for exactly this purpose. Returns `label`, `limit`, `limit_remaining`, `usage`, `is_free_tier`. A bad key cannot produce a 200 |
| Gemini | `GET /v1beta/openai/models` with `Authorization: Bearer <key>` | Genuinely authenticated here — §1 recorded an HTTP 400 on an invalid key |

`ProviderConfig` gains a `validatePath` (or a small strategy field) distinct from `modelsPath`. `modelsNeedAuth: false` must no longer be read as "validation is free".

**Two bonuses from `/api/v1/key`,** both directly useful to the UI the plan already wants: `limit_remaining` gives the credit display in §7.2 a real source instead of an estimate, and `is_free_tier` tells the app whether the user is on the 50/day or 1,000/day rate limit (§4) — so the rate-limit error message can be accurate instead of generic.

**Untested:** whether `GET /api/v1/key` answers a browser preflight with CORS headers. Everything else in §1 did, but this endpoint was not among the four tested. **Test it before M9.2 builds Connect** — it is a five-minute check on the same spike page, and if it fails, key validation needs a different design rather than a different URL.
