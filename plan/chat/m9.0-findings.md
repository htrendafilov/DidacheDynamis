### 1a. Anthropic — the browser header is exactly the mechanism

Proven in both directions.

- With the header: `access-control-allow-origin: *` on the preflight; browser reads the response.
- Without it: preflight returns HTTP 400 and **no** `access-control-allow-origin`; browser reports "No 'Access-Control-Allow-Origin' header is present" and `fetch` throws.

The preflight must also declare the header in `Access-Control-Request-Headers`, which the browser does automatically. A curl test that omits it will wrongly look like a failure.

**Resolves the open question in `m9.2-workspace-and-provider.md` §1:** `GET /v1/models` works through the OpenAI-compatibility layer with `Authorization: Bearer`. The dummy-key response is `{"type":"error","error":{"type":"authentication_error","message":"Invalid bearer token"}}` — the endpoint accepted the auth *scheme* and rejected only the token's validity. **No static model list is needed.** Confirm once with a valid key.

### 1b. Gemini — works, contrary to the plan's assumption

`https://generativelanguage.googleapis.com/v1beta/openai` responds to a browser `POST /chat/completions` with a readable HTTP 400 (`"Please pass a valid API key"`), and the preflight from `https://bible.trendafilovi.net` returns `access-control-allow-origin: https://bible.trendafilovi.net`.

`Authorization: Bearer` is accepted — the error concerns key *validity*, not the auth method. **A key in the URL is not required**, so the §4.2 rule against credentials in URLs is not violated.

The plan marked Gemini "gated on the spike, undocumented". It is now cleared, with the caveat that this behaviour is still undocumented by Google and could change without notice. Keep the provider registry row easy to remove.

### 1c. OpenAI — the interesting failure

The plan said `api.openai.com` "sends no CORS headers". That is **not accurate**, and the real behaviour is a trap:

| Request | Result |
|---|---|
| `OPTIONS /v1/chat/completions` preflight | HTTP 200 with `access-control-allow-origin` **echoing the requesting origin** — both `https://bible.trendafilovi.net` and `http://localhost:8080` |
| The actual `POST /v1/chat/completions` | HTTP 401 with **no** `access-control-allow-origin` header |
| Browser outcome | Blocked. `Failed to fetch`, "No 'Access-Control-Allow-Origin' header is present on the requested resource" |
| `GET /v1/models` from a browser | **Works** — readable 401 |

OpenAI's CORS support is endpoint-inconsistent: the preflight handler answers, the completions response does not carry the header, and the models endpoint does.

**Consequence for anyone re-testing this:** a curl preflight check alone reports success and is wrong. Verify with a real browser request that reads the response body. The conclusion stands — OpenAI direct is unusable — but the reason is narrower than "no CORS at all", and someone will re-open this if the reason is recorded imprecisely.

OpenAI models remain reachable through OpenRouter.

## 2. Final `connect-src`

```
connect-src 'self' https://api.dropboxapi.com https://content.dropboxapi.com
            https://openrouter.ai https://api.anthropic.com
            https://generativelanguage.googleapis.com
```

`https://api.openai.com` is **not** included — nothing would be able to use it.

**Check 1 passed in both directions.** With the committed CSP, all four origins were blocked with `effectiveDirective: "connect-src"` and zero requests left the browser. After adding the origins, all four requests went out and the CSP violation list was empty. The CSP is genuinely enforced and is the control.

## 4. Rate limits and catalogue shape

**Free-tier limits** (openrouter.ai/docs/api/reference/limits, 2026-07-29):

- 20 requests/minute
- 50 requests/day without credit; **1,000/day once $10 in credits has ever been purchased**

**Catalogue** — `GET https://openrouter.ai/api/v1/models`, unauthenticated, 367 models.

- Top-level: `data`, `total_count`, `links`
- Per model: `id`, `canonical_slug`, `hugging_face_id`, `name`, `created`, `description`, `context_length`, `architecture`, `pricing`, `top_provider`, `per_request_limits`, `supported_parameters`, `default_parameters`, `supported_voices`, `knowledge_cutoff`, `expiration_date`, `links`, `reasoning`
- `pricing`: `prompt`, `completion`, `input_cache_read`, `input_cache_write`, `overrides` — strings, price per token
- Tool support is detected via `"tools" in supported_parameters`

The model picker in M9.2 should show `name`, `id`, `context_length`, and `pricing.prompt`/`pricing.completion`, and filter on `id`/`name`.

`openrouter/free` exists: 200,000 context, `pricing` `{prompt: "0", completion: "0"}`, and `tools` in `supported_parameters`.

### 4a. Correction to the plan's §5.4

The plan claims requesting tool-calling "shrinks the free pool", used as an argument for deferring the tool loop. Measured today: **14 of the 15 free entries support tools** (only `nvidia/nemotron-3.5-content-safety:free` does not), and `openrouter/free` itself advertises `tools`.

That argument is therefore weak and should be dropped from `interactive_chat_plan.md` §10. The remaining reasons to defer the tool loop to M9.6 are unaffected and still sufficient: determinism, testability, and structurally bounding network access instead of bounding it by policy.
